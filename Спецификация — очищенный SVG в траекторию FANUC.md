# Спецификация: «очищенный SVG → траектория → программа FANUC»

## Проект «Линия индустрии». Модуль `svg2fanuc`

> Статус: рабочая спецификация для разработки MVP.
>
> **Реализация MVP начата 8 сентября 2026 года** — код в папке `svg2fanuc/`

> `robot.ini`), выставочный диспетчер (этап 4), backend ROS 2 (этап 5).
> Подробности — `svg2fanuc/README.md`.
>
> Дата исследования готовых решений: 8 сентября 2026 года.
>
> Документ продолжает «Техническую реализацию — от изображения к траектории
> робота.md» и начинается после этапа очистки SVG. Векторизация PNG, генерация
> изображения нейросетью и художественная очистка линий сюда не входят.

> Под FANUC здесь понимается робот с контроллером семейства R-30iB Plus либо
> R-50iA. Точная модель и версия контроллера должны быть заданы профилем ячейки.

## 1. Результат исследования и принятое направление

### 1.1. Короткий вывод

Готовое решение, наиболее близкое к задаче «положить SVG и получить программу
робота», — **RoboDK**: в официальной документации есть импорт SVG, Curve Follow
Project, пример рисования SVG через Python API и постпроцессор FANUC. Это
законченный путь, но production-использование RoboDK требует лицензии.

У FANUC есть **ROBOGUIDE HandlingPRO с CAD-to-Path**, но публичная документация
подтверждает работу с CAD-геометрией, а не прямой контракт «очищенный SVG →
программа». Для нашего процесса потребуется промежуточный импорт кривых через
DXF/CSV и ручная либо автоматизированная настройка проекта.

С 2025 года FANUC развивает официальный открытый **ROS 2 Driver**. Он позволяет
передавать рассчитанные траектории реальному или виртуальному роботу через
`ros2_control` и MoveIt, но сам SVG не разбирает. Кроме того, для физического
робота нужны совместимый контроллер, подходящая версия ПО и опции J519 Stream
Motion + R912 Remote Motion либо пакет S636.

**Решение для MVP:** написать небольшую детерминированную утилиту `svg2fanuc`,
которая преобразует очищенный SVG в текстовую FANUC-программу `.LS`, отчет и
предпросмотр. Затем `.LS` компилируется в `.TP` через `MakeTP` из WinOLPC /
ROBOGUIDE или загружается напрямую при наличии опции ASCII Upload.

**Вторая очередь:** при подтвержденных опциях контроллера добавить backend
ROS 2 / MoveIt для проверки кинематики и потокового исполнения. SVG-конвейер и
внутренний формат траектории при этом не меняются.

### 1.2. Обзор готовых решений

| Решение | Что уже умеет | Что остается сделать | Ограничения | Решение для проекта |
|---|---|---|---|---|

| **Пример RoboDK “Drawing an SVG image”** | Готовый Python-пример разбора SVG и программирования рисующего робота | Адаптировать под конкретный FANUC и требования безопасности | Это пример, а не готовый выставочный сервис | Использовать как референс поведения и тестовый oracle |
| **FANUC ROBOGUIDE HandlingPRO / CAD-to-Path** | Цифровая ячейка FANUC, CAD-to-Path, проверка движения, программы контроллера | Конвертировать SVG в поддерживаемые кривые, построить и настроить процесс | Модуль и лицензия должны реально присутствовать; headless-интеграция не подтверждена | Основной инструмент проверки ячейки и `.LS/.TP`; не ядро SVG-конвертера |

| **Robots for Rhino/Grasshopper** | Открытый плагин, симуляция и генерация vendor-specific программ, включая FANUC | Импортировать/подготовить кривые в Rhino и собрать Grasshopper-схему | Требует Rhino 8; не готовый headless SVG-сервис | Подходит для ручного прототипирования, не для MVP-сервиса |
| **Visual Components OLP** | CAD-кривые, path solver, проверка коллизий, постпроцессоры FANUC | Подготовить импорт геометрии и автоматизацию | Коммерческий OLP; прямой SVG-конвейер публично не подтвержден | Альтернатива, если лицензия уже есть у интегратора |
| **Собственный `SVG → FANUC LS`** | Полный контроль контракта, детерминизм, нулевая стоимость библиотек, удобный запуск “на лету” | Реализовать парсерный слой, план траектории, LS-emitter и тесты | Не решает сам по себе IK и коллизии; нужен квалифицированный профиль ячейки и проверка | **Основной путь MVP** |

По результатам поиска не найдено бесплатной production-ready утилиты с узким
контрактом «очищенный SVG → проверенная программа FANUC» в один вызов. Это вывод
по рассмотренным официальным продуктам и основным открытым проектам, а не
утверждение об отсутствии любого частного решения в мире.

### 1.3. Почему MVP не должен сразу стримить движения

Генерация `.LS/.TP` отделяет подготовку задания от выполнения. Файл можно
просмотреть, скомпилировать, проверить и только после подтверждения оператора
загрузить в контроллер. Потоковое управление добавляет сеть и внешний ПК в
контур исполнения и требует дополнительных FANUC-опций.

Для открытия выставки “в реальном времени” достаточно, чтобы новая программа
создавалась и проверялась после получения SVG за приемлемое время. Непрерывный
стриминг точек не является обязательным условием живого интерактива.

## 2. Цель, границы и допущения

### 2.1. Цель

Создать Python-пакет и CLI `svg2fanuc`, которые:

1. принимают очищенный SVG и профиль роботизированной ячейки;
2. безопасно разбирают разрешенное подмножество SVG;
3. переводят кривые в полилинии с погрешностью, заданной в миллиметрах;
4. размещают рисунок в системе координат холста;
5. добавляют подходы, контактное рисование, подъемы и переходы;
6. выполняют геометрическую валидацию;
7. создают нейтральный план движения и FANUC `.LS`;
8. формируют визуальный предпросмотр, метрики и воспроизводимый manifest;
9. при наличии WinOLPC компилируют `.LS` в `.TP` через `MakeTP`;
10. никогда не запускают физический робот без отдельного подтвержденного слоя.

### 2.2. Входит в MVP

- плоская рабочая поверхность;
- один инструмент и один цвет;
- фиксированная ориентация TCP относительно холста;
- геометрия из линий и незалитых путей;
- FANUC LS как основной аппаратно-зависимый выход;
- дробление длинного задания на подпрограммы;
- офлайн-предпросмотр и отчет;
- ручной операторский шлюз перед загрузкой и запуском.

### 2.3. Не входит в MVP

- PNG, centerline-векторизация и очистка SVG;
- интерпретация заливок, градиентов, ширины и цвета штриха;
- поддержание силы контакта программой;
- компенсация неплоскостности по карте поверхности;
- автоматическое управление кистями, краской и сменой инструмента;
- самостоятельная inverse kinematics в `svg2fanuc`;
- автоматический запуск реального робота;
- утверждение безопасности ячейки программным отчетом;
- произвольная 3D-поверхность.

### 2.4. Базовые допущения

- поверхность откалибрована как FANUC `UFRAME`;
- TCP инструмента откалиброван как `UTOOL`;
- локальная плоскость рисунка — `Z = z_draw`, положительный Z направлен от
  поверхности к роботу;
- положение поверхности, фиксированные `W/P/R` и `CONFIG` заранее проверены на
  всей разрешенной прямоугольной области;
- податливость контакта обеспечивает механический подпружиненный держатель;
- DCS, ограждение, сканер и другие safety-функции проектирует интегратор.

## 3. Контракт входного SVG

### 3.1. Канонический профиль `SVG-DRAW-1`

Утилита обязана принимать только явно ограниченное подмножество SVG. Входной
файл считается “очищенным”, если выполняются все требования:

- UTF-8, расширение `.svg`, без gzip;
- корневой элемент `<svg>`;
- задан корректный `viewBox="minX minY width height"`, `width > 0`, `height > 0`;
- рисунок состоит из групп `<g>` и геометрии `<path>`, `<polyline>`,
  `<polygon>`, `<line>`, `<circle>`, `<ellipse>` и `<rect>`;
- после применения всех наследуемых transforms каждый видимый элемент может
  быть преобразован в один или несколько незалитых путей;
- `fill="none"`; штрих интерпретируется по центральной линии независимо от его
  экранной толщины;
- разрывы подпутей (`M`) являются границами физических штрихов;
- в координатах нет `NaN`, `Inf`, нечисловых значений и экстремальных величин;
- нет дублирующихся подряд точек и нулевых штрихов;
- художественная геометрия уже очищена от паразитных узлов.

Разрешенные команды `path`: `M/m`, `L/l`, `H/h`, `V/v`, `C/c`, `S/s`, `Q/q`,
`T/t`, `A/a`, `Z/z`. Кривые и дуги разрешены: лишние узлы во входе не нужны,
поскольку программа сама выполнит адаптивный flattening после перевода масштаба
в миллиметры.

### 3.2. Запрещенные конструкции

MVP отклоняет файл целиком, если встречаются:

- `<text>`, `<image>`, `<foreignObject>`, `<script>`, animation;
- `<use>` и внешние ссылки;
- DTD, entity, XInclude, processing instruction и `xml-stylesheet`;
- `href`, `xlink:href`, URL в стилях;
- clip path, mask, filter, pattern, marker и gradient;
- CSS из внешнего файла;
- заполненные фигуры;
- вложенный SVG с отдельным viewport;
- неизвестный элемент, способный влиять на геометрию.

Неподдерживаемая геометрия не должна молча исчезать: результат — ошибка с
указанием элемента и его `id`.

### 3.3. Размерные единицы

SVG допускает собственные единицы, `viewBox`, viewport и цепочки transforms.
Парсер сначала приводит все элементы к пользовательским координатам корневого
`viewBox`, а физический размер задает **профиль ячейки**, не `width/height` SVG.

Это устраняет неоднозначность между `px`, `mm`, `pt` и DPI. Режим
`scale_mode: physical` можно добавить позже; в MVP поддерживается только
`scale_mode: fit_viewbox`.

## 4. Пользовательский интерфейс программы

### 4.1. Команды CLI

```bash
# Проверить вход и построить отчет без FANUC-кода
svg2fanuc inspect drawing.svg --profile cell.yaml --out build/job_001

# Создать нейтральную траекторию, preview, manifest и FANUC LS
svg2fanuc generate drawing.svg --profile cell.yaml --out build/job_001

# Дополнительно скомпилировать LS → TP, если настроен MakeTP
svg2fanuc compile build/job_001/manifest.json

# Проверить ранее созданный job и контрольные суммы
svg2fanuc verify build/job_001/manifest.json
```

### 4.2. Коды завершения

| Код | Значение |
|---:|---|
| 0 | Успешно |
| 2 | Ошибка CLI или профиля |
| 3 | Невалидный/неподдерживаемый SVG |
| 4 | Геометрия не проходит ограничения |
| 5 | Превышен бюджет точек/программ |
| 6 | Ошибка генерации LS |
| 7 | Ошибка MakeTP |
| 8 | Нарушена целостность manifest |
| 9 | Внутренняя ошибка |

При любой ошибке `.LS` и `.TP` не публикуются в итоговую директорию. Временные
файлы пишутся отдельно, а результат переносится атомарно только после успеха.

### 4.3. Выходные артефакты

```text
job_001/
├── normalized.svg       # разрешенная геометрия с примененными transforms
├── preview.svg          # рисунок, переходы, границы холста и точки старта
├── trajectory.json      # vendor-neutral план движений
├── report.json          # метрики, warnings, результат проверок
├── manifest.json        # SHA-256, версии, профиль и список артефактов
├── ART00001.LS          # master либо единственная программа
├── A0000101.LS          # подпрограммы при дроблении
└── ART00001.TP          # опционально после MakeTP
```

`preview.svg` отображает:

- черным — контактные линии;
- красным пунктиром — переходы на `z_clear`;
- зеленым — начало каждого штриха;
- синей рамкой — разрешенную область;
- оранжевой рамкой — поле безопасности;
- подпись с job ID, масштабом и количеством точек.

## 5. Архитектура

```text
clean.svg + cell.yaml
        │
        ▼
[A] secure SVG gate
        │
[B] parse + apply viewBox/transforms
        │
[C] shapes/subpaths → ordered strokes
        │
[D] scale into canvas coordinates (mm)
        │
[E] adaptive curve flattening in millimetres
        │
[F] remove numerical duplicates + validate geometry
        │
[G] optional stroke routing (never changes drawn geometry)
        │
[H] add clear/plunge/draw/retract motions
        │
[I] vendor-neutral trajectory.json
        ├───────────────┐
        ▼               ▼
[J] preview/report   [K] FANUC LS emitter
                         │
                         ▼
                    [L] MakeTP (optional)
                         │
                         ▼
                  operator / ROBOGUIDE gate
```

### 5.2. Библиотеки MVP

| Библиотека | Роль | Лицензия/примечание |
|---|---|---|
| Python 3.12+ | CLI и orchestration | Зафиксировать minor-версию в окружении |
| `svgelements` | SVG shapes, paths, viewBox и transforms | MIT; ориентирован на полное соблюдение SVG и умеет приводить shapes к paths |
| `defusedxml` | Предварительный безопасный XML-разбор | Защита от DTD/entity/external reference классов атак |

предпроцессором. Если routing собственного модуля окажется недостаточным,
допускается опциональный backend `vpype`, зафиксированный конкретной версией.

## 6. Внутренняя модель данных

### 6.1. Геометрия

```python
Point2 = tuple[float, float]       # миллиметры в UFRAME холста

Stroke:
    id: str
    source_element_id: str | None
    points: list[Point2]
    closed: bool
    reversible: bool
```

Инварианты `Stroke`:

- минимум две различные точки;
- нет соседних точек ближе `dedupe_epsilon_mm`;
- все координаты конечны;
- весь штрих лежит внутри разрешенного прямоугольника;
- максимальная ошибка flattening не превышает `flatness_mm`;
- направление можно менять только целиком, без перестановки внутренних точек.

### 6.2. Нейтральный план движений

```python
Motion:
    kind: "LINEAR" | "CALL" | "SET_FRAME" | "SET_TOOL" | "COMMENT"
    phase: "ENTRY" | "TRAVEL" | "PLUNGE" | "DRAW" | "RETRACT" | "EXIT"
    xyz_mm: [float, float, float] | null
    wpr_deg: [float, float, float] | null
    speed: float | str | null
    termination: "FINE" | "CNT"
    cnt: int | null
    stroke_id: str | null
```

`trajectory.json` — единственный источник для всех emitters. FANUC-специфичный
синтаксис не должен проникать в `svg_reader`, flattening и routing.

### 6.3. Состояния задания

```text
REJECTED
GENERATED_UNCOMPILED
COMPILED_UNVERIFIED
VERIFIED_FOR_CELL
APPROVED_BY_OPERATOR
```

`svg2fanuc` создает максимум `COMPILED_UNVERIFIED`. Последующие статусы ставит
внешний диспетчер после проверки цифровой ячейки и оператора. Компиляция TP
подтверждает синтаксическую совместимость, но не безопасность движения.

## 7. Алгоритм преобразования

### 7.1. Безопасный разбор

До геометрического парсера выполнить отдельный XML gate:

1. проверить размер файла;
2. запретить DTD, entities и внешние ссылки через `defusedxml`;
3. обойти дерево и проверить allowlist элементов и атрибутов;
4. отклонить URL, data URI, скрипты, CSS и неизвестные namespaces;
5. ограничить глубину дерева, число элементов и длину атрибутов;
6. только после этого передать байты в `svgelements` без загрузки внешних
   ресурсов.

### 7.2. Нормализация SVG

1. Разрешить root `viewBox`.
2. Применить transforms корня, групп и элементов в правильном порядке.
3. Преобразовать basic shapes в paths.
4. Разбить каждый path по командам `Move` на физические штрихи.
5. Сохранить исходный порядок элементов и подпутей.
6. Записать `normalized.svg` без групповых transforms и неподдерживаемых данных.

Если корневой `viewBox` отсутствует, MVP завершает работу ошибкой. Угадывать его
по `width/height` или bbox нельзя.

### 7.3. Размещение на холсте

Пусть bbox рисунка после transforms равен `(xmin, ymin, xmax, ymax)`, размеры
холста — `canvas_width` и `canvas_height`, поле — `margin`. Тогда размеры
доступной области: `W = canvas_width − 2 × margin` и
`H = canvas_height − 2 × margin`.

Для `fit: contain`:

```text
s = min(W / (xmax - xmin), H / (ymax - ymin))
x_mm = margin + align_x + s × (x_svg - xmin)
y_mm = margin + align_y + s × (ymax - y_svg)
```

Инверсия Y обязательна, потому что экранная ось SVG обычно направлена вниз, а
ось Y пользовательской системы холста задается при калибровке. `align_x` и
`align_y` вычисляются по режиму `center`, `top_left` или явному offset.

Допускаются режимы:

- `contain` — вписать с сохранением пропорций, основной;
- `actual` — использовать масштаб `svg_units_per_mm` из профиля;
- `stretch` — запрещен в production, доступен только с `--allow-distortion`.

### 7.4. Flattening кривых

Flattening выполняется **после определения масштаба**, чтобы допуск был задан в
физических миллиметрах.

Для Line дополнительная дискретизация не выполняется. Для quadratic/cubic
Bezier и arc используется рекурсивное деление, пока одновременно не выполнены:

- максимальное отклонение кривой от хорды `≤ flatness_mm`;
- длина хорды `≤ max_segment_mm`;
- глубина рекурсии `≤ max_subdivision_depth`.

Если лимит глубины достигнут раньше допуска, задание отклоняется. После
flattening удаляются только численно совпадающие соседние точки. Повторное
Douglas–Peucker-упрощение в MVP выключено: вход уже очищен, и программа не
должна незаметно менять художественную линию.

Инженерные начальные значения для тестов, не утвержденные для реального робота:

```yaml
flatness_mm: 0.25
max_segment_mm: 5.0
dedupe_epsilon_mm: 0.01
max_subdivision_depth: 20
```

### 7.5. Порядок штрихов

По умолчанию `routing.mode: preserve`: порядок SVG сохраняется.

Опциональный `nearest`:

1. начать из `travel_start_xy`;
2. выбрать ближайший конец еще не выполненного штриха;
3. развернуть открытый штрих, если его конец ближе начала;
4. для замкнутого штриха выбрать ближайшую существующую вершину как старт;
5. после greedy-прохода выполнить ограниченный 2-opt только между штрихами.

Routing не вправе:

- менять внутреннюю геометрию;
- разрывать открытый штрих;
- объединять штрихи;
- менять порядок между `data-order-group`, если такой атрибут разрешен профилем.

В отчете сохраняются длины холостого пути до и после оптимизации.

### 7.6. Добавление движений инструмента

Для каждого штриха:

```text
LINEAR start(x, y, z_clear)   TRAVEL   FINE
LINEAR start(x, y, z_draw)    PLUNGE   FINE
LINEAR p1(x, y, z_draw)       DRAW     CNTn
...
LINEAR end(x, y, z_draw)      DRAW     FINE
LINEAR end(x, y, z_clear)     RETRACT  FINE
```

Переходы между штрихами выполняются линейно на `z_clear`, а не произвольным
суставным движением. Это медленнее, но оставляет TCP в заранее проверенной
плоскости свободного перемещения.

Вход в рабочую область и выход из нее должны выполняться отдельными,
отрепетированными на реальной ячейке программами `CELL_IN` и `CELL_OUT`. Их
имена задаются профилем; генератор только вставляет `CALL`. Суставные перемещения
из HOME не генерируются из SVG.

### 7.7. Скорость и сглаживание

- `PLUNGE` и `RETRACT`: низкая линейная скорость, `FINE`.
- первая и последняя точки штриха: `FINE`.
- промежуточные точки гладкой линии: малый настраиваемый `CNT`.
- острый художественный угол: `FINE` либо отдельный малый `CNT` по порогу угла.
- `TRAVEL`: линейная скорость на `z_clear`, `FINE` у точки опускания.

`CNT` меняет фактическую форму траектории. Его значение нельзя считать чисто
производственным параметром: оно входит в художественные и приемочные тесты.

## 8. FANUC LS emitter

### 8.1. Выходной контракт

Emitter получает только валидированный `trajectory.json` и профиль. Он создает:

- секции `/PROG`, `/ATTR`, `/MN`, `/POS`, `/END`;
- выбор `UFRAME_NUM` и `UTOOL_NUM`;
- Cartesian positions с фиксированными `W/P/R` и `CONFIG`;
- `L`-инструкции с literal speed и termination;
- `CALL CELL_IN` до рисунка и `CALL CELL_OUT` после;
- подпрограммы при достижении настроенного лимита.

Пример формы, а не готовая программа для запуска:

```text
/PROG  ART00001
/ATTR
... controller-specific attributes ...
/MN
   1:  UFRAME_NUM=1 ;
   2:  UTOOL_NUM=1 ;
   3:  CALL CELL_IN ;
   4:L P[1] 250mm/sec FINE ;
   5:L P[2] 40mm/sec FINE ;
   6:L P[3] 100mm/sec CNT3 ;
   7:L P[4] 100mm/sec FINE ;
   8:L P[5] 40mm/sec FINE ;
   9:  CALL CELL_OUT ;
/POS
P[1]{
   GP1:
   UF : 1, UT : 1, CONFIG : 'N U T, 0, 0, 0',
   X = 100.000 mm, Y = 200.000 mm, Z = 15.000 mm,
   W = 180.000 deg, P = 0.000 deg, R = 0.000 deg
};
...
/END
```

Точная шапка `/ATTR`, допустимые имена, `CONFIG` и синтаксис проверяются
`MakeTP` на `robot.ini`, соответствующем реальному контроллеру. Нельзя считать
успешную генерацию текста доказательством совместимости.

### 8.2. Дробление программы

Лимиты строк и памяти различаются между конфигурациями контроллера, поэтому они
не зашиваются в код как “лимит FANUC”. Профиль содержит консервативный
`max_motion_lines_per_subprogram`, подтвержденный тестом на целевой ячейке.

Правила:

- не разрезать контактный штрих посередине;
- каждая подпрограмма начинается и заканчивается при поднятом инструменте;
- `CELL_IN` и `CELL_OUT` вызываются master-программой один раз;
- позиции нумеруются независимо внутри каждого файла;
- master вызывает части строго по manifest;
- если один штрих превышает лимит, задание отклоняется с предложением увеличить
  допуск flattening или художественно разбить штрих до повторной очистки SVG.

### 8.3. Компиляция и перенос

FANUC `.LS` — текстовый offline-формат, а исполняемый файл — `.TP`. Есть две
поддерживаемые ветки:

1. **ASCII Upload присутствует:** контроллер принимает `.LS` и преобразует его
   при загрузке.
2. **ASCII Upload отсутствует:** `MakeTP` из FANUC WinOLPC/ROBOGUIDE компилирует
   `.LS` в `.TP`; требуется `robot.ini` от совместимой виртуальной ячейки.

MVP не загружает и не запускает файл автоматически. FTP/USB/другой транспорт —
за пределами `svg2fanuc` и реализуется отдельным диспетчером после приемки.

  draw_speed_mm_s: 100.0

  enabled: false

входит по SHA-256 в manifest каждого задания. Изменение TCP, UFRAME, основания,
холста, робота, контроллера или инструмента требует новой версии профиля и
повторной квалификации.

## 10. Валидация и безопасность

### 10.1. Что проверяет `svg2fanuc`

- корректность SVG и allowlist;
- конечность и диапазон координат;
- bbox и каждую точку относительно разрешенной области;
- допуск flattening;
- минимальную длину штрихов и сегментов;
- максимальное число штрихов, точек и движений;
- общую длину рисунка и переходов;
- оценочное время;
- последовательность фаз `TRAVEL → PLUNGE → DRAW → RETRACT`;
- отсутствие travel-движений на контактном Z;
- соответствие каждой позиции одному UFRAME/UTOOL/orientation/config;
- структуру и имена LS-программ;
- успешную компиляцию MakeTP, если она включена.

### 10.2. Что программа принципиально не может подтвердить сама

- достижимость всех поз конкретным роботом;
- отсутствие сингулярностей и смены конфигурации руки;
- отсутствие столкновений звеньев, инструмента и оборудования;
- правильность физической калибровки TCP/UFRAME;
- допустимое усилие на поверхность;
- достаточность DCS, ограждений и других safety-функций;
- безопасность для посетителей.

В UI и `report.json` должна присутствовать явная строка:

> GENERATED ≠ SAFE TO RUN. Требуются квалифицированный профиль ячейки,
> проверка интегратором и подтверждение оператора.

### 10.3. Квалификация прямоугольной рабочей области

Для интерактива нельзя вручную симулировать каждую новую картинку в течение
нескольких минут. До выставки интегратор должен квалифицировать **всю область**,
в которой разрешено генерировать линии:

1. откалибровать TCP и UFRAME;
2. проверить углы, периметр и сетку точек холста на `z_draw` и `z_clear`;
3. подтвердить одну ориентацию и конфигурацию руки;
4. проверить переходы по всей clear-plane;
5. смоделировать инструмент, основание, поверхность и ограждение в ROBOGUIDE;
6. установить DCS Position/Speed Check и внешние safety-устройства по оценке
   риска;
7. выполнить тест низкой скоростью на реальной установке;
8. подписать и заморозить production-профиль.

Геометрический валидатор затем не выпускает ни одной точки за пределы этой
квалифицированной области. Такой подход допустим только после письменного
решения интегратора; спецификация не объявляет его safety-сертификацией.

### 10.4. Operator gate

Перед каждым запуском оператор видит:

- normalized и preview;
- bbox, число штрихов/точек;
- длину и оценочное время;
- предупреждения;
- статус MakeTP;
- hash профиля и задания;
- подтверждение, что инструмент поднят и рабочая зона свободна.

Кнопка запуска должна находиться во внешнем приложении, а не в `svg2fanuc`.
Повторный запуск возможен только для того же SHA-256 набора артефактов.

## 11. Ошибки, логирование и воспроизводимость

### 11.1. Ошибки домена

| Код | Пример |
|---|---|
| `SVG_XML_UNSAFE` | DTD, entity или внешняя ссылка |
| `SVG_ELEMENT_UNSUPPORTED` | `<text>` или `<image>` |
| `SVG_VIEWBOX_REQUIRED` | Нет root viewBox |
| `SVG_FILL_UNSUPPORTED` | Обнаружена заливка |
| `SVG_EMPTY` | Нет рисуемых штрихов |
| `GEOM_NONFINITE` | NaN/Inf |
| `GEOM_OUT_OF_BOUNDS` | Точка за разрешенным полем |
| `GEOM_FLATTEN_LIMIT` | Не достигнут допуск до max depth |
| `GEOM_POINT_BUDGET` | Превышено число точек |
| `MOTION_INVALID_PHASE` | Нарушен подъем/контакт |
| `LS_PROGRAM_TOO_LARGE` | Штрих нельзя безопасно разбить |
| `LS_EMIT_FAILED` | Ошибка генерации текста |
| `MAKETP_FAILED` | Компилятор отверг LS |
| `PROFILE_NOT_QUALIFIED` | В production-профиле есть TBD |

### 11.2. Логи

- структурированный JSON log;
- `job_id`, версия приложения и hash входа в каждой записи;
- без содержимого SVG и персональных данных в обычном log;
- отдельные audit events для генерации, компиляции и подтверждения;
- traceback только в developer mode.

### 11.3. Детерминизм

Одинаковые SVG, профиль и версия программы должны давать одинаковые:

- `normalized.svg`;
- `trajectory.json`;
- геометрию `preview.svg`;
- `.LS` без учета явно выделенного timestamp;
- метрики и порядок штрихов.

Manifest содержит SHA-256 входа, профиля и всех outputs, версии Python и
зависимостей, время генерации и флаг production/development.

## 12. Тестирование

### 12.1. Unit-тесты

- все команды SVG path, абсолютные и относительные;
- transforms на root/group/element;
- `viewBox` с ненулевыми `minX/minY`;
- circle/ellipse/rect/polygon → path;
- несколько `M` внутри одного path;
- открытые и замкнутые штрихи;
- инверсия Y и выравнивание;
- адаптивный flattening Bezier и arc;
- routing preserve/reverse/closed-loop start;
- sharp corner → FINE;
- корректные plunge/retract;
- дробление без разрыва контактного штриха;
- детерминированность.

### 12.2. Негативные и security-тесты

- DTD/entity/XXE/XML bomb;
- `<image href="file://...">`, HTTP URL и data URI;
- script/foreignObject/use;
- глубоко вложенные группы;
- огромный path attribute;
- NaN/Inf/overflow;
- нулевой viewBox;
- заливки и скрытая неподдерживаемая геометрия;
- слишком много точек;
- один штрих больше лимита подпрограммы;
- выход на 0,001 мм за допустимую область.

### 12.3. Golden tests

Минимальный набор:

1. горизонталь/вертикаль/диагональ;
2. квадрат с острыми углами;
3. окружность и эллиптическая дуга;
4. cubic и quadratic Bezier;
5. 20 раздельных штрихов с неудачным входным порядком;
6. рисунок на границах разрешенного поля;
7. реальный очищенный SVG проекта;
8. стресс-файл около лимита точек.

Для каждой версии сравниваются `trajectory.json`, preview, report и `.LS`.
Синтаксис `.LS` проверяется MakeTP на robot.ini целевой ячейки.

### 12.4. Интеграционные тесты

1. `SVG → LS → TP` без предупреждений.
2. Импорт TP/LS в ROBOGUIDE.
3. Симуляция всей программы без unreachable, singularity и collision events.
4. Выполнение теста на физическом роботе в T1/пониженной скорости.
5. Измерение отклонения нарисованной линии от preview.
6. Проверка аварийной остановки, паузы и безопасного повторного старта.

- Форматирование/lint/test запускаются одной командой.
- Производственный профиль read-only для учетной записи выставочного приложения.

## 15. Критерии приемки MVP

MVP принят, если одновременно выполнено следующее:

1. Все валидные файлы профиля `SVG-DRAW-1` преобразуются без ручной правки.
2. Все запрещенные конструкции отклоняются до геометрического parser-а.
3. Максимальная геометрическая ошибка flattening не больше значения профиля.
4. Ни одна draw/travel point не выходит за квалифицированную область.
5. В каждом штрихе корректны clear → plunge → draw → retract.
6. Routing не меняет контактную геометрию.
7. Длинные задания дробятся только между штрихами.
8. `.LS` компилируется MakeTP под целевой `robot.ini` либо успешно принимается
   целевым контроллером через ASCII Upload.
9. Preview визуально соответствует симуляции в ROBOGUIDE.
10. Один реальный очищенный SVG проекта нарисован на тестовой поверхности на
    пониженной скорости.
11. Повторная генерация идентичного задания дает идентичные hashes.
12. Физический запуск невозможен непосредственно из CLI `svg2fanuc`.
