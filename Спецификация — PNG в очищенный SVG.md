# Спецификация: «PNG → очищенный SVG»

## Проект «Линия индустрии». Модуль `png2svg`

> Статус: рабочая спецификация для разработки MVP.
>
> Дата исследования готовых решений: 8 сентября 2026 года.
>
> Документ покрывает **первую половину** программного конвейера: от растрового
> изображения, сгенерированного нейросетью, до **очищенного векторного файла
> SVG**, пригодного для передачи роботу.
>
> Вторая половина — «очищенный SVG → траектория → программа FANUC» — описана
> в отдельном документе **«Спецификация — очищенный SVG в траекторию FANUC.md»**
> (модуль `svg2fanuc`). Настоящая спецификация обязана выдавать SVG, который
> без единой правки принимается входным контрактом того модуля (профиль
> `SVG-DRAW-1`, раздел 3 того документа).

---

## 1. Цель, границы, стык

### 1.1. Что делает `png2svg`

Python-пакет и CLI. Один вызов:

```
png2svg generate drawing.png --profile raster.yaml --out build/job_001
```

принимает растровый рисунок и профиль обработки, выдаёт **очищенный SVG** из
осевых линий штрихов плюс предпросмотр и метрики.

Задачи модуля:

1. привести растр к чёткой чёрно-белой битовой маске;
2. извлечь **центральные линии** штрихов (скелет), а не их контуры;
3. собрать из скелета топологический граф и убрать артефакты (шпоры, дребезг,
   ложные узлы на пересечениях);
4. перевести штрихи в полилинии и **убрать лишние точки** (упрощение по допуску);
5. слить разорванные штрихи, отсортировать порядок, выбросить мусорные обрезки;
6. записать SVG строго по контракту `SVG-DRAW-1`;
7. сформировать `preview.svg` и `stats.json`.

### 1.2. Что вне границ

- генерация изображения нейросетью — отдельный блок конвейера;
- любые сведения о роботе, ячейке, системах координат, ROBOGUIDE, `.LS/.TP` —
  это зона `svg2fanuc`;
- физический размер рисунка в миллиметрах: `png2svg` выдаёт **масштабно-
  независимый** SVG (координаты в единицах `viewBox`), физический размер задаёт
  профиль ячейки уже в `svg2fanuc`;
- инструмент, краска, усилие прижима;
- полутоновые заливки и штриховка как художественная задача — вынесены в
  опциональный модуль (раздел 7), по умолчанию выключен.

### 1.3. Граница ответственности со `svg2fanuc`

| Задача | Где |
|---|---|
| Бинаризация, шумоподавление растра | `png2svg` |
| Извлечение осевых линий (skeleton/centerline) | `png2svg` |
| Обрезка шпор, чистка графа скелета | `png2svg` |
| **Упрощение полилиний, удаление лишних точек** | `png2svg` |
| Слияние разорванных штрихов, сортировка, фильтр мусора | `png2svg` |
| Запись SVG по контракту `SVG-DRAW-1` | `png2svg` |
| Безопасный разбор SVG, применение `viewBox`/transforms | `svg2fanuc` |
| Масштабирование в координаты холста (мм) | `svg2fanuc` |
| Адаптивный flattening кривых в миллиметрах | `svg2fanuc` |
| Подходы/отходы, план движений, FANUC `.LS`, `MakeTP` | `svg2fanuc` |
| Валидация ячейки в ROBOGUIDE, operator gate | `svg2fanuc` / диспетчер |

`png2svg` **не должен** пытаться делать работу `svg2fanuc` и наоборот. Единственный
интерфейс между ними — файл `clean.svg`.

## 2. Контракт входа и выхода

### 2.1. Вход

| Параметр | Тип | Описание |
|---|---|---|
| `image` | PNG / JPG / BMP | растр, желательно тёмное на светлом фоне, любое разрешение |
| `--profile` | YAML | профиль обработки (раздел 8) |
| `--engine` | `skeleton \| autotrace` | движок центральных линий (по умолч. `skeleton`) |
| `--simplify` | число (ед. `viewBox`) | допуск упрощения; переопределяет профиль |
| `--canvas-hint` | `WxH` мм | опц.: если известен итоговый холст, допуск упрощения можно задать в мм через `--simplify-mm` |
| `--simplify-mm` | мм | опц.: физический допуск, пересчитывается в единицы `viewBox` по `--canvas-hint` |
| `--out` | путь | директория результатов |
| `--dry-run` | флаг | только `preview.svg` и `stats.json`, без `clean.svg` |
| `--strict` | флаг | ненулевой код возврата при любом warning |

### 2.2. Выход

```text
job_001/
├── clean.svg        # очищенный SVG по контракту SVG-DRAW-1 — ЕДИНСТВЕННЫЙ вход для svg2fanuc
├── preview.svg      # осевые линии + точки старта + порядок обхода (для человека)
├── skeleton.png     # отладка: битовая маска скелета (по флагу --debug)
├── stats.json       # метрики
└── manifest.json    # SHA-256 входа, версии, профиль, список артефактов
```

### 2.3. Гарантии формата `clean.svg` (соответствие `SVG-DRAW-1`)

Эмиттер обязан выдавать файл, для которого верно **всё**:

| Требование `SVG-DRAW-1` | Как обеспечивает `png2svg` |
|---|---|
| UTF-8, `.svg`, без gzip | пишем UTF-8 без сжатия |
| корневой `<svg>` с корректным `viewBox`, `width>0`, `height>0` | `viewBox="0 0 W H"` в пикселях рабочего растра (после апскейла), `width`/`height` в тех же единицах |
| геометрия только из разрешённого набора элементов | эмитим только `<polyline>` (открытые штрихи) и `<polygon>` (замкнутые) внутри одной `<g>` |
| после transforms всё → незалитые пути | **transforms не используем вообще**; координаты абсолютные |
| `fill="none"`, штрих = центральная линия | `fill="none"` на `<g>` и на каждом элементе; ширина линии чисто визуальная (`stroke-width="1"`) |
| разрывы подпутей (`M`) = границы штрихов | один элемент SVG = один физический штрих; многосегментных `M` не создаём |
| нет `NaN`, `Inf`, экстремальных чисел | валидируем перед записью; координаты в диапазоне `viewBox` |
| нет дублирующихся подряд точек, нет нулевых штрихов | dedupe по `epsilon`, фильтр по минимальной длине |
| геометрия очищена от паразитных узлов | обрезка шпор + упрощение Дугласа–Пекера — основная работа модуля |
| запрещены `text/image/use/script/animation/clip/mask/filter/pattern/marker/gradient/внешний CSS/DTD/entity/вложенный svg/заливки` | ничего из этого не эмитим в принципе |

Дополнительно эмиттер проставляет `id` каждому штриху (`s0001`, `s0002`, …) —
это разрешено контрактом и помогает `svg2fanuc` указывать проблемный элемент в
ошибках.

Пример `clean.svg`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 1280 1044"
     width="1280" height="1044">
  <g fill="none" stroke="#000000" stroke-width="1"
     stroke-linecap="round" stroke-linejoin="round">
    <polyline id="s0001" points="120.0,880.5 121.2,640.0 121.0,180.4"/>
    <polyline id="s0002" points="300.4,860.1 720.9,540.2"/>
    <polygon  id="s0003" points="980.1,300.0 1040.6,300.4 1041.0,470.9 980.5,470.2"/>
  </g>
</svg>
```

### 2.4. Метрики `stats.json`

`strokes`, `points`, `open_strokes`, `closed_strokes`, `total_length_vb`
(в единицах `viewBox`), `bbox_vb`, `points_removed_by_simplify`,
`spurs_pruned`, `strokes_merged`, `dropped_short_strokes`,
`travel_length_before`, `travel_length_after` (метрика сортировки),
`viewbox`, `source_image_size`, `upscale_factor`.

## 3. Архитектура конвейера

```text
PNG
 │  [A] загрузка, grayscale, опц. апскейл          Pillow / OpenCV
 ▼
grayscale
 │  [B] бинаризация + шумоподавление               scikit-image (Otsu,
 ▼                                                   remove_small_objects, closing)
битовая маска (bool)
 │  [C] скелетизация                               scikit-image skeletonize (Zhang–Suen / Lee)
 ▼
1-px скелет
 │  [D] граф из скелета                            sknw.build_sknw → узлы + рёбра-полилинии
 ▼
граф
 │  [E] чистка графа: обрезка шпор, слияние узлов,  свой код на графе
 │      разбор замкнутых петель
 ▼
полилинии (в пикселях viewBox)
 │  [F] упрощение — удаление лишних точек           Douglas–Peucker (vpype linesimplify / rdp)
 ▼
 │  [G] слияние разорванных штрихов, сортировка,    vpype: linemerge, filter, linesort, reloop
 ▼      выброс мусора
очищенные штрихи
 │  [H] валидация против SVG-DRAW-1                 свой валидатор
 ▼
 │  [I] запись clean.svg + preview.svg + stats      свой эмиттер
 ▼
clean.svg  ──▶  вход модуля svg2fanuc
```

Этапы [C]–[E] изолированы за интерфейсом «маска → список полилиний», поэтому
движок можно заменить на `autotrace -centerline` (`--engine autotrace`) без
изменения остального конвейера.

## 4. Ресёрч: выбор библиотек

### 4.1. Векторизация — почему скелетизация, а не трассировка контура

| Инструмент | Тип | Годится? |
|---|---|---|
| **potrace** | обводка контура (заливка) | ❌ двойная линия на каждый штрих |
| **vtracer** | обводка / цветовые области | ❌ только outline/fill, центральных линий нет (README, MIT) |
| **autotrace `-centerline`** | центральная линия | ⚠️ классика, но капризен к порогу, падает на сложных картинках, ставится сборкой из исходников |
| **Inkscape 1.2–1.3 «Centerline tracing (autotrace)»** / плагин `inkscape-centerline-trace` | центральная линия | ⚠️ тот же autotrace внутри + автоподбор порога; GUI, для ручной проверки |
| **scikit-image `skeletonize` + `sknw`** | скелет → граф → полилинии | ✅ **выбор**: чистый Python, детерминизм, полный контроль обрезки и упрощения, `pip install`, BSD/MIT |
| **DrawingBotV3** | image → «скетч»-SVG, много стилей пера | ⚠️ бесплатный (Java), но это художественная стилизация, а не точное повторение линий; порядок путей не оптимизирует |

Базовый движок — **скелетизация Zhang–Suen (scikit-image)** + построение графа
через **sknw**. `autotrace -centerline` — альтернативный фронтенд для сравнения
качества на конкретных картинках. Трассировщики контура (potrace/vtracer) — только
в опциональном модуле заливок (раздел 7).

### 4.2. Упрощение и оптимизация путей — vpype

**vpype** (MIT, `pip install vpype`) — стандарт де-факто в плоттер-сообществе.
Используемые команды:

| Команда | Что делает | По умолчанию |
|---|---|---|
| `linemerge --tolerance` | склеивает пути с близкими концами в один | 0.5 px `viewBox` |
| `linesimplify --tolerance` | упрощение по Дугласу–Пекеру — **удаление лишних точек** | 0.8 px `viewBox` |
| `filter --min-length` | выбрасывает мусорные обрезки | 2 px `viewBox` |
| `linesort` (`--two-opt`) | переупорядочивает штрихи, минимизируя холостой ход | — |
| `reloop` | сдвигает точку старта замкнутых контуров | — |

Пример строки обработки промежуточного SVG:

```
vpype read raw.svg \
  linemerge --tolerance 0.5 \
  linesimplify --tolerance 0.8 \
  filter --min-length 2 \
  linesort --two-opt \
  reloop \
  write clean_raw.svg
```

Вызываем как подпроцесс — так проще фиксировать версию и воспроизводимость.
Если промежуточный `vpype` окажется недостаточным, упрощение делаем своим `rdp`
(Ramer–Douglas–Peucker), а `vpype` оставляем только на `linemerge`/`linesort`.

**Важно:** упрощение выполняет именно `png2svg`. Модуль `svg2fanuc` по своему
контракту повторный Douglas–Peucker **не делает** — он рассчитывает на уже
очищенный вход. Поэтому качество прореживания здесь — часть приёмочных тестов.

### 4.3. Два уровня удаления лишних точек

1. **По топологии графа [E]**: удаление шпор короче `spur_len`, слияние узлов
   ближе `node_merge_dist`, объединение почти коллинеарных сегментов. Работает
   до перевода в геометрический допуск.
2. **Геометрическое [F]**: Douglas–Peucker по допуску в единицах `viewBox`.
   Даёт основное сокращение точек (обычно −70…−90 %) и убирает «лесенку»
   1-px скелета.

### 4.4. Допуск упрощения и физический масштаб

`png2svg` работает в пикселях `viewBox` и по умолчанию не знает итогового размера
холста. Допуск задаётся:

- напрямую в пикселях `viewBox` (`--simplify` / профиль) — режим MVP;
- либо в миллиметрах (`--simplify-mm`) при указанном `--canvas-hint WxH`:
  `tol_px = simplify_mm × min(viewBox_w / canvas_w_mm, viewBox_h / canvas_h_mm)`.

Ориентир: при растре ~1000–1500 px по короткой стороне допуск 0.6–1.2 px
безопасен визуально. Финальный адаптивный flattening (0.25 мм) выполняется позже
в `svg2fanuc` и на художественную линию не влияет.

### 4.5. Вход из готового вектора

Если на вход подан не PNG, а уже векторный файл — это **не** зона `png2svg`.
Такой файл идёт напрямую в `svg2fanuc` (или прогоняется через внешний `vpype`
вручную). `png2svg` работает только с растром.

### 4.6. Итоговый стек

```text
Pillow / OpenCV     загрузка, grayscale, апскейл
scikit-image        бинаризация, шумоподавление, скелетизация
sknw                скелет → граф
numpy / shapely     операции на полилиниях, обрезка шпор, rdp
vpype               упрощение (linesimplify) и оптимизация (linemerge/linesort)
lxml / xml.sax      запись SVG (без внешних сущностей)
pytest              тесты
```

Все библиотеки открытые (BSD/MIT/Apache). Ни одного платного пункта.

## 5. Модули: детали реализации

### 5.1. [A] Загрузка и нормализация

- PNG/JPG/BMP; RGBA → композит на белый фон; → grayscale.
- Если короткая сторона `< upscale_min_short_side` (по умолч. 900) — бикубический
  апскейл до этого размера. `viewBox` итогового SVG считается по **растру после
  апскейла**; коэффициент пишется в `stats.json`.
- EXIF-поворот игнорируем (машинная генерация).

### 5.2. [B] Бинаризация и шумоподавление

- Порог: `threshold_otsu`. Флаг `--adaptive` → `cv2.adaptiveThreshold`.
- Рисунок = `True` (штрихи).
- `remove_small_objects(min_size=remove_small_objects_px)` — убрать точки-мусор.
- `binary_closing` со структурным элементом 1–2 px — закрыть микроразрывы от
  антиалиасинга. `--bridge-gap N` — радиус закрытия бо́льших разрывов (осторожно:
  склеивает близкие штрихи).

### 5.3. [C] Скелетизация

- `skeletonize(mask)` (Zhang–Suen). Для толстых штрихов (> ~12 px) —
  `skeletonize(mask, method='lee')`.
- Результат — 1-px связный скелет.

### 5.4. [D] Граф

- `graph = sknw.build_sknw(skeleton, multi=True)`.
- Узлы — концы и точки ветвления/пересечения; рёбра — полилинии
  `graph[u][v][k]['pts']` (массив `(row, col)`).

### 5.5. [E] Чистка графа

- **Обрезка шпор**: рекурсивно удалять рёбра, у которых один конец — узел
  степени 1, а длина `< spur_len_px` (1–3 % короткой стороны).
- **Слияние узлов**: узлы ближе `node_merge_dist_px` объединять (артефакты
  скелета на пересечениях — мелкие треугольники).
- **Замкнутые петли**: sknw выдаёт как ребро `u == v` — ставим разрыв в
  геометрически удобной вершине, помечаем штрих `closed=True`.
- **Спрямление**: объединять последовательные почти коллинеарные микросегменты
  (угол `< collinear_deg`).
- Опциональное сглаживание лесенки (Chaikin 1–2 итерации, `--smooth`) — по
  умолчанию выключено, полагаемся на [F].
- Выход: список полилиний в пикселях `viewBox` + флаг «замкнутая» + `id`.

### 5.6. [F] Упрощение (удаление лишних точек)

- Douglas–Peucker с допуском `simplify_tol` (единицы `viewBox`).
- Для замкнутых — циклический вариант, стартовая вершина сохраняется.
- Пост-проверки качества: доля выброшенной суммарной длины линий (`> 3 %` →
  warning), максимальное отклонение упрощённой линии от исходной (в метрики).
- dedupe соседних точек ближе `dedupe_epsilon`.

### 5.7. [G] Слияние, сортировка, фильтр

- `linemerge` (`merge_tol`): склеить штрихи, чьи концы почти совпадают
  (типично после скелета на разорванных линиях).
- `filter --min-length` (`min_stroke_len`): выбросить обрезки-мусор.
- `linesort --two-opt`: минимизировать суммарный холостой ход между штрихами;
  открытые штрихи можно разворачивать. Метрики «до/после» в `stats.json`.
- `reloop`: рандомизировать старт замкнутых контуров (чтобы не копился след в
  одной точке).
- Порядок и развороты штрихов менять **можно** (это не художественная
  геометрия); внутреннюю геометрию штриха — **нельзя**.

### 5.8. [H] Валидация против `SVG-DRAW-1`

Перед записью прогнать собственный чек-лист из таблицы 2.3 плюс:

- все координаты конечны и внутри `[0, viewBox_w] × [0, viewBox_h]`;
- у каждого штриха ≥ 2 различных точки;
- нет соседних дубликатов;
- только `<polyline>`/`<polygon>`, без transforms, `fill="none"`.

Опционально (флаг `--verify-with-svg2fanuc`) — прогнать `clean.svg` через
`svg2fanuc inspect` и убедиться в коде возврата 0. Это лучший интеграционный
тест стыка.

### 5.9. [I] Эмиттер SVG и предпросмотр

- `clean.svg` — раздел 2.3.
- `preview.svg`: чёрным — штрихи; зелёным — точка старта каждого штриха; тонким
  серым пунктиром — холостые переходы в порядке обхода; подпись с числом
  штрихов/точек и `viewBox`. Это то, что смотрит человек до передачи роботу.
- `stats.json`, `manifest.json` (SHA-256 входа, профиля, всех выходов; версии
  Python и зависимостей; флаг production/development).

## 6. Детерминизм и воспроизводимость

Одинаковые PNG, профиль и версия программы дают идентичные `clean.svg`,
`preview.svg` (геометрия), `stats.json`. Порядок штрихов и результат `linesort`
детерминированы (фиксированный tie-break, без случайного seed либо seed из
профиля). `manifest.json` фиксирует все хеши и версии.

---

## 7. Опциональный модуль заливок (по умолчанию выключен)

Если нейросеть выдаёт сплошные чёрные области, а не только тонкие штрихи:

- детекция крупных заполненных компонент (площадь `> fill_area_px`);
- контур компоненты — `potrace`/`vtracer` (outline) → незамкнутый/замкнутый путь
  по краю;
- внутренняя штриховка — плагин `hatched` для `vpype` (или `vpype-flow-imager`)
  с шагом `hatch_pitch` и углом `hatch_angle`;
- тонкие штрихи того же изображения по-прежнему идут через скелет;
- всё объединяется перед этапом [F] и на выходе остаётся набором незалитых
  полилиний — контракт `SVG-DRAW-1` не нарушается.

Включается `--fills hatch --hatch-pitch 3 --hatch-angle 45` (шаг в единицах
`viewBox`).

## 8. Профиль обработки (YAML)

```yaml
schema_version: 1
profile_id: raster_default_v1

image:
  upscale_min_short_side: 900
  otsu: true
  adaptive: false
  remove_small_objects_px: 20
  bridge_gap_px: 1

skeleton:
  engine: skeleton              # skeleton | autotrace
  method: auto                  # auto | zhang | lee
  spur_len_px: 12
  node_merge_dist_px: 4
  collinear_deg: 4
  smooth_chaikin_iterations: 0

simplify:
  tolerance_vb: 0.8             # единицы viewBox (Douglas–Peucker)
  dedupe_epsilon_vb: 0.05
  max_length_loss_ratio: 0.03  # warning при превышении

paths:
  merge_tol_vb: 0.5
  min_stroke_len_vb: 2.0
  linesort_two_opt: true
  reloop: true

fills:
  enabled: false
  fill_area_px: 4000
  hatch_pitch_vb: 3.0
  hatch_angle_deg: 45

output:
  emit_ids: true
  stroke_width: 1
  decimal_places: 2
  verify_with_svg2fanuc: false

limits:
  max_input_bytes: 33554432
  max_strokes: 20000
  max_points: 400000
```

Профиль версионируется и входит по SHA-256 в `manifest.json`. Он **не содержит**
ничего про робота, ячейку и координаты холста — это принадлежит профилю
`svg2fanuc`.

## 9. Обработка ошибок и краевые случаи

| Код | Причина |
|---:|---|
| 0 | успех |
| 2 | ошибка CLI или профиля |
| 3 | не удалось прочитать/декодировать изображение |
| 4 | пустое или почти пустое изображение (нет штрихов после бинаризации) |
| 5 | превышен бюджет штрихов/точек |
| 6 | ошибка векторизации (скелет распался, граф пуст) |
| 7 | выход не проходит собственную валидацию `SVG-DRAW-1` |
| 8 | `--verify-with-svg2fanuc` вернул ошибку |
| 9 | внутренняя ошибка |

| Случай | Поведение |
|---|---|
| Цветное изображение / градиент | автопорог, warning |
| Рваные штрихи | `bridge_gap_px`; много компонент → warning с их числом |
| Точек больше бюджета | итеративно поднять `simplify.tolerance_vb`; при неуспехе — ошибка 5 |
| Потеря длины линий при упрощении `> max_length_loss_ratio` | warning (в `--strict` — ошибка) |
| Замкнутые контуры | разрыв в стартовой вершине, флаг `closed` |
| Самопересечения после упрощения | допустимо для рисунка, не чиним |
| `autotrace` не установлен при `--engine autotrace` | ошибка 2 с подсказкой |

При любой ошибке `clean.svg` в итоговую директорию не публикуется (пишем во
временную, переносим атомарно только при успехе).

## 10. Тестирование

### 10.1. Unit / компонентные

- бинаризация на чистом и зашумлённом растре;
- скелет прямой, диагонали, пересечения (X-узел), кривой, кольца;
- обрезка шпор заданной длины;
- слияние ложных узлов на пересечении;
- Douglas–Peucker: число точек падает, отклонение ≤ допуска;
- замкнутая петля → `closed`, старт сохранён;
- `linemerge` склеивает разорванную линию, `linesort` уменьшает холостой ход;
- детерминизм: повтор даёт идентичные хеши.

### 10.2. Негативные

- пустой/белый лист → ошибка 4;
- «снег» из точек → всё отфильтровано, ошибка 4 либо пустой валидный SVG (по
  флагу);
- гигантский растр → ошибка 5 либо корректный апскейл-даунскейл;
- битый PNG → ошибка 3.

### 10.3. Golden tests

Набор PNG и эталонных `clean.svg`:

1. горизонталь / вертикаль / диагональ;
2. решётка вертикалей с диагональю поверх (пересечения) — **референс проекта**;
3. квадрат с острыми углами;
4. окружность и дуга;
5. плавная кривая (проверка, что упрощение не «ограняет» её грубо);
6. 20 раздельных штрихов в неудачном исходном порядке (проверка `linesort`);
7. рисунок с тонкими штрихами и одной заливкой (модуль разделов 7);
8. стресс-файл около лимита точек.

Для каждой версии сравниваются `clean.svg` (геометрия с допуском), `preview.svg`
(перцептивно, SSIM) и `stats.json`.

### 10.4. Интеграционные

1. `png2svg` → `clean.svg` → `svg2fanuc inspect` — код возврата 0, без warnings
   контракта.
2. Полный конвейер PNG → `clean.svg` → `svg2fanuc generate` → `.LS` →
   (в `svg2fanuc`) `MakeTP` / ROBOGUIDE.
3. Визуальное совпадение `preview.svg` (`png2svg`) и `preview.svg` (`svg2fanuc`)
   после масштабирования — рисунок не «поехал» на стыке.

## 11. Нефункциональные требования

- Кроссплатформенно (Linux/macOS/Windows); ROBOGUIDE и `MakeTP` здесь не нужны.
- Время `generate` для растра ~1500×1200 и ~10 000 выходных точек — цель `≤ 5 с`
  на выставочном ПК.
- Пиковая память — `≤ 500 МБ` для входа в пределах лимитов.
- Никакой сети.
- Воспроизводимая установка из lock-файла, все зависимости зафиксированы точными
  версиями.
- Публичный API покрыт type hints; lint/format/test — одной командой.

## 12. Этапы реализации

### Этап 1. Векторизация и предпросмотр

- [A]–[E] + `preview.svg` + `stats.json`.
- Критерий: референс проекта распознаётся как одиночные линии, без двойных
  контуров; шпоры вырезаны.

### Этап 2. Упрощение и оптимизация

- [F]–[G]: интеграция `vpype`, бюджет точек, метрики «до/после».
- Критерий: −70…−90 % точек без визуальной деградации на golden set; потеря
  длины линий в пределах `max_length_loss_ratio`.

### Этап 3. Эмиттер и стык со `svg2fanuc`

- [H]–[I]: запись `clean.svg`, собственный валидатор, `manifest.json`.
- Прогон `--verify-with-svg2fanuc` на всём golden set.
- Критерий: 100 % golden `clean.svg` принимаются `svg2fanuc inspect` без правок.

### Этап 4. Опциональный модуль заливок

- Раздел 7 — если это потребуется по картинкам от нейросети.

### Этап 5. Обвязка «на лету»

- Режим слежения за папкой / HTTP-эндпойнт `POST /vectorize` (PNG → `clean.svg`),
  чтобы дальше подхватывал диспетчер `svg2fanuc`.
- Цель по времени «изображение → `clean.svg`» — до ~5 с.

## 13. Критерии приёмки MVP

1. Любой валидный PNG со штриховой Ч/Б-графикой даёт `clean.svg` без ручной
   правки.
2. Осевые линии, а не контуры: ни одного «двойного» штриха на golden set.
3. Шпоры и дребезг скелета вырезаны по заданным порогам.
4. Упрощение убирает лишние точки в пределах допуска; потеря длины линий не
   больше `max_length_loss_ratio`.
5. `clean.svg` формально соответствует `SVG-DRAW-1` и принимается
   `svg2fanuc inspect` с кодом 0 на всём golden set.
6. Порядок обхода уменьшает суммарный холостой ход относительно исходного.
7. Повторная генерация идентичного задания даёт идентичные хеши.
8. `png2svg` нигде не пытается генерировать `.LS`, знать про робота или ячейку.

## 14. Открытые вопросы

1. Что реально выдаёт нейросеть — только тонкие штрихи (как референсы) или ещё
   сплошные заливки и полутона? От этого зависит, нужен ли модуль раздела 7.
2. Нужен ли режим «физический масштаб» (`--simplify-mm` + `--canvas-hint`) уже в
   MVP, или пиксельного допуска достаточно.
3. Допустима ли лёгкая художественная стилизация линии (сглаживание, вариативная
   плотность точек) или требуется максимально точное повторение силуэта.
4. Максимальное время «изображение → `clean.svg`» для живого интерактива.
5. Где физически стыкуются `png2svg` и `svg2fanuc` — один процесс, папка обмена
   или HTTP.
